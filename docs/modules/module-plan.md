# Module Build Plan

Generated and maintained by `module-planner`. Source inputs: `docs/figma/screen-inventory.md`, `docs/figma/design-system-notes.md`, `docs/figma/coverage-report.md`, `agent.md` (Ezitech Engineering Framework MERN-009), `docs/agent-rules.md`, `docs/workflow-state.md`.

No application codebase exists yet (confirmed in `docs/figma/coverage-report.md`). All modules start at `PLANNED`; all frontend screens start at `PLANNED` (not yet `BUILT`).

## Build Principles

- Build in dependency order.
- One module per `module-builder` invocation.
- Frontend screens are owned by the `frontend-screen-builder` workflow — this plan maps screens to modules but does not build them.
- A module cannot be marked complete until its required frontend screens and backend/integration work pass their quality gates (per `docs/orchestration-protocol.md`).
- If a module's required screens are not yet `BUILT`, `module-builder` must stop and instruct the user to run the frontend screen workflow first (agent-rules.md §6).

## Dependency-tier rationale

1. **Foundational/shared** — MOD-001 (Shell/Bootstrap). Every other screen renders inside this shell.
2. **Authentication/authorization dependencies** — MOD-002 (Auth/Session), MOD-003 (RBAC/Permissions). Nothing behind a login wall can be built without these.
3. **Data/source dependencies** — MOD-004 (Organization Management, multi-tenant root), MOD-005 (User Management, scoped under org+role).
4. **Core business workflows** — MOD-006 (Data Sources), MOD-007 (Destinations), MOD-008 (Pipeline Builder & Execution).
5. **Secondary workflows** — MOD-009 (Analytics/Monitoring Dashboards) — reports on data produced by tier 4.
6. **Reporting/admin/support** — MOD-010 (Notifications) — cross-cutting event/notification delivery, closes the loop across all prior modules.

- **Integration**: frontend screens call the real backend endpoints (not local mocks) unless a mock boundary is explicitly labeled per agent-rules.md §5; `organizationId` scoping verified end-to-end for tenant-owned modules (MOD-004 through MOD-010).
- **Permissions**: every mutating and sensitive-read endpoint enforces the MOD-003 permission model; cross-organization access is denied and tested.
- **Error/loading/empty states**: present and reviewed for every screen with dynamic data (all modules except none — every module here has dynamic data).
- **Responsiveness/accessibility**: not applicable beyond the desktop-only reference viewport (1440px) documented in `docs/figma/design-system-notes.md`, since no responsive/mobile Figma variants exist; keyboard/basic accessibility behavior per agent-rules.md §5 still applies.
- Module is not marked `DONE` until `ui-reviewer`, `integration-reviewer`, and `tester` have all run and passed per `docs/agent-rules.md` §8 and `docs/orchestration-protocol.md`.
